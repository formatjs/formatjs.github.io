This guide covers setting up FormatJS polyfills for React Native with the Hermes JavaScript engine. Hermes ships with partial Intl support, so you need to polyfill the missing APIs.

Experimental Rust Intl extensions#

The repository includes Rust Intl.getCanonicalLocales, Intl.supportedValuesOf, Intl.Locale, Intl.PluralRules, Intl.ListFormat, Intl.DisplayNames, Intl.Segmenter, Intl.Collator, Intl.NumberFormat, Intl.RelativeTimeFormat, Intl.DateTimeFormat and Intl.DurationFormat implementations with C++ JSI adapters. SDK 0.1.0 packages public headers, adapter source, extension JavaScript, and Rust static libraries for Linux x86_64 GNU and macOS arm64. Consumers compile the adapter against their matching Hermes JSI headers and link SDK targets :canonical_locales, :supported_values, :locale and :pluralrules, :listformat, :displaynames, :segmenter, :collator, :numberformat, :relativetimeformat, :datetimeformat, :durationformat from @formatjs_intl_getcanonicallocales_hermes.

The SDK is built from this repository and is not published to BCR, npm, or crates.io. It does not include Android/iOS artifacts or React Native package installation. Follow the native SDK instructions and independent consumer example to build, extract, and install its public layout.

#include <formatjs/hermes/canonical_locales.h>
#include <formatjs/hermes/supported_values.h>
#include <formatjs/hermes/intl_locale.h>
#include <formatjs/hermes/intl_pluralrules.h>
#include <formatjs/hermes/intl_listformat.h>
#include <formatjs/hermes/intl_displaynames.h>
#include <formatjs/hermes/intl_segmenter.h>
#include <formatjs/hermes/intl_collator.h>
#include <formatjs/hermes/intl_numberformat.h>
#include <formatjs/hermes/intl_relativetimeformat.h>
#include <formatjs/hermes/intl_datetimeformat.h>
#include <formatjs/hermes/intl_durationformat.h>

formatjs::installCanonicalLocales(*runtime);
formatjs::installSupportedValuesOf(*runtime);
formatjs::installLocale(*runtime);
formatjs::installCanonicalLocales(*runtime);
formatjs::installPluralRules(*runtime);
formatjs::installListFormat(*runtime);
formatjs::installDisplayNames(*runtime);
formatjs::installSegmenter(*runtime);
formatjs::installCollator(*runtime);
formatjs::installNumberFormat(*runtime);
formatjs::installRelativeTimeFormat(*runtime);
auto dateTime = formatjs::installDateTimeFormat(*runtime);
formatjs::installDurationFormat(*runtime);

Install before application scripts. For bytecode-only startup, compile the SDK's js/extensions.js with the matching hermesc, evaluate it into a setup object, then pass that object to each installer, for example formatjs::installPluralRules(*runtime, extensions). For Hermes core/contrib registration, add js/30-IntlGetCanonicalLocales.js to its extension source list and call the same overload from the compiled C++ dispatcher. Linking the SDK alone does not register a startup hook.

Install trusted Intl.Locale before the final adapter installation. If Locale needs Intl.getCanonicalLocales first, install the adapter, load Locale, then reinstall before application code, then install PluralRules and ListFormat so they capture the final canonicalizer.

PluralRules starts without locale data. Ship selected SDK files from locale-data/pluralrules/<locale>.json, then register their UTF-8 text when needed:

type NativePluralRules = typeof Intl.PluralRules & {
  __addLocaleData(...packs: string[]): void
}

function loadPluralLocale(jsonText: string) {
  ;(Intl.PluralRules as NativePluralRules).__addLocaleData(jsonText)
}

Loading another pack updates supported locales. Existing instances keep their data, including when a loaded locale is replaced. The standalone SDK consumer loads English first and French later, and tests BigInt selection and ranges.

Rust callers can disable the canonicalizer crate's default compiled_data feature and use Canonicalizer::try_new_with_provider(&provider) with caller-loaded ICU data. The current JSI installer uses the compiled-data path; provider injection into the native installer is separate work.

The desktop benchmark compares it with @formatjs/intl-getcanonicallocales inside the same Hermes runtime:

bazel run -c opt //benchmarks/intl-canonicalization:benchmark

Run the Rust unit tests, Hermes differential tests, and upstream Test262 cases:

bazel test -c opt //crates/intl_getcanonicallocales:intl_getcanonicallocales_test \
  //benchmarks/intl-canonicalization:conformance_test \
  //tools/hermes-test262:getcanonicallocales_test

These measurements exclude startup. Benchmark on target Android/iOS devices before choosing a backend.

Hermes Intl support#

Hermes includes built-in support for some Intl APIs but not all. The following table shows what's available natively and what needs polyfilling:

APIHermes supportPolyfill package
Intl.NumberFormatPartial (basic)@formatjs/intl-numberformat
Intl.DateTimeFormatPartial (basic)@formatjs/intl-datetimeformat
Intl.PluralRulesYes@formatjs/intl-pluralrules (for older Hermes)
Intl.LocaleYes@formatjs/intl-locale (for older Hermes)
Intl.RelativeTimeFormatNo@formatjs/intl-relativetimeformat
Intl.ListFormatNo@formatjs/intl-listformat
Intl.DisplayNamesNo@formatjs/intl-displaynames
Intl.DurationFormatNo@formatjs/intl-durationformat
Intl.SegmenterNo@formatjs/intl-segmenter
Intl.getCanonicalLocalesYes@formatjs/intl-getcanonicallocales (for older Hermes)
Check your Hermes version

Hermes Intl support evolves between versions. Use the shouldPolyfill function from each package to detect at runtime whether a polyfill is actually needed.

Installation#

Install only the polyfills your app requires:

npm i @formatjs/intl-locale @formatjs/intl-pluralrules @formatjs/intl-numberformat @formatjs/intl-datetimeformat @formatjs/intl-relativetimeformat @formatjs/intl-getcanonicallocales react-intl

Polyfill load order#

Polyfills must be loaded in dependency order. Some polyfills depend on others being present first. Load them in your app entry point before any formatting code runs.

polyfills.ts

import {shouldPolyfill as shouldPolyfillGetCanonicalLocales} from '@formatjs/intl-getcanonicallocales/should-polyfill'
import {shouldPolyfill as shouldPolyfillLocale} from '@formatjs/intl-locale/should-polyfill'
import {shouldPolyfill as shouldPolyfillPluralRules} from '@formatjs/intl-pluralrules/should-polyfill'
import {shouldPolyfill as shouldPolyfillNumberFormat} from '@formatjs/intl-numberformat/should-polyfill'
import {shouldPolyfill as shouldPolyfillDateTimeFormat} from '@formatjs/intl-datetimeformat/should-polyfill'
import {shouldPolyfill as shouldPolyfillRelativeTimeFormat} from '@formatjs/intl-relativetimeformat/should-polyfill'

export async function loadPolyfills(locale: string) {
  // 1. getCanonicalLocales — no deps
  if (shouldPolyfillGetCanonicalLocales()) {
    await import('@formatjs/intl-getcanonicallocales/polyfill')
  }

  // 2. Locale — depends on getCanonicalLocales
  if (shouldPolyfillLocale()) {
    await import('@formatjs/intl-locale/polyfill')
  }

  // 3. PluralRules — depends on Locale
  if (shouldPolyfillPluralRules(locale)) {
    await import('@formatjs/intl-pluralrules/polyfill-force')
    await import(`@formatjs/intl-pluralrules/locale-data/${locale}`)
  }

  // 4. NumberFormat — depends on PluralRules, Locale
  if (shouldPolyfillNumberFormat(locale)) {
    await import('@formatjs/intl-numberformat/polyfill-force')
    await import(`@formatjs/intl-numberformat/locale-data/${locale}`)
  }

  // 5. DateTimeFormat — depends on Locale
  if (shouldPolyfillDateTimeFormat(locale)) {
    await import('@formatjs/intl-datetimeformat/polyfill-force')
    await import(`@formatjs/intl-datetimeformat/locale-data/${locale}`)
    // Add timezone data if needed
    await import('@formatjs/intl-datetimeformat/add-all-tz')
  }

  // 6. RelativeTimeFormat — depends on PluralRules, Locale
  if (shouldPolyfillRelativeTimeFormat(locale)) {
    await import('@formatjs/intl-relativetimeformat/polyfill-force')
    await import(`@formatjs/intl-relativetimeformat/locale-data/${locale}`)
  }
}
Load Order Matters

Intl.NumberFormat depends on Intl.PluralRules, which depends on Intl.Locale, which depends on Intl.getCanonicalLocales. Loading them out of order will cause errors.

Selective locale data#

Each polyfill ships locale data for 700+ locales. In React Native, bundle every locale data file you import — there's no tree-shaking at the file level.

Only import the locales your app supports:

// Good — only 3 locales
import '@formatjs/intl-numberformat/locale-data/en'
import '@formatjs/intl-numberformat/locale-data/fr'
import '@formatjs/intl-numberformat/locale-data/de'

If your app supports many locales, use dynamic import() to load them on demand (see the polyfills.ts example above).

For @formatjs/intl-datetimeformat, timezone data is also significant. If you only need a few timezones, import them selectively instead of using add-all-tz:

import '@formatjs/intl-datetimeformat/add-golden-tz'

Locale matching performance#

In React Native, some polyfills auto-register all supported locales. When @formatjs/intl-localematcher performs locale matching against 700+ available locales, the naive algorithm was extremely slow (~610ms on Hermes).

@formatjs/intl-localematcher includes a three-tier optimization that reduced this to ~1.4ms (439x faster):

  1. O(1) exact match — Set lookup for exact locale strings
  2. Subtag fallback — Maximize locale and remove subtags progressively
  3. CLDR distance — Full UTS #35 algorithm with memoization (rare path)

This optimization is automatic — no configuration needed. See the Performance Tuning guide for more details.

Metro bundler configuration#

React Native uses Metro. If you pre-compile messages to AST and want to alias away the parser (see Performance Tuning), configure Metro's resolver:

metro.config.js

const {getDefaultConfig, mergeConfig} = require('@react-native/metro-config')

const config = {
  resolver: {
    // Alias the parser to the no-parser build
    resolveRequest(context, moduleName, platform) {
      if (moduleName === '@formatjs/icu-messageformat-parser') {
        return context.resolveRequest(
          context,
          '@formatjs/icu-messageformat-parser/no-parser',
          platform
        )
      }
      return context.resolveRequest(context, moduleName, platform)
    },
  },
}

module.exports = mergeConfig(getDefaultConfig(__dirname), config)

Using react-intl#

Once polyfills are loaded, react-intl works the same as on the web:

App.tsx

import {IntlProvider, FormattedMessage, useIntl} from 'react-intl'
import {Text, View} from 'react-native'
import {useEffect, useState} from 'react'
import {loadPolyfills} from './polyfills'

const messages = {
  greeting: 'Hello, {name}!',
  itemCount: 'You have {count, plural, one {# item} other {# items}}.',
}

function HomeScreen() {
  const intl = useIntl()
  return (
    <View>
      <Text>{intl.formatMessage({id: 'greeting'}, {name: 'World'})}</Text>
      <Text>{intl.formatMessage({id: 'itemCount'}, {count: 5})}</Text>
    </View>
  )
}

export default function App() {
  const [ready, setReady] = useState(false)

  useEffect(() => {
    loadPolyfills('en').then(() => setReady(true))
  }, [])

  if (!ready) return null

  return (
    <IntlProvider locale="en" messages={messages}>
      <HomeScreen />
    </IntlProvider>
  )
}

Troubleshooting#

RangeError: invalid locale at startup#

A polyfill dependency is missing. Check the load order — make sure @formatjs/intl-getcanonicallocales and @formatjs/intl-locale are loaded first.

Slow initial render#

If your app loads many locales eagerly, the locale matcher may be doing expensive CLDR distance calculations. The @formatjs/intl-localematcher optimization handles this automatically since v0.5.10, but verify you're on a recent version.

Missing timezone data#

@formatjs/intl-datetimeformat requires explicit timezone data imports. If you see incorrect timezone behavior, add @formatjs/intl-datetimeformat/add-all-tz or selectively import the timezones you need.

Rust ListFormat locale data#

Link SDK target :listformat. Ship selected JSON packs from locale-data/listformat/; load their text through your application's file or network loader before constructing formatters:

const ListFormat = Intl.ListFormat as typeof Intl.ListFormat & {
  __addLocaleData(...packs: string[]): void
}
ListFormat.__addLocaleData(frenchJsonText)
new ListFormat('fr').format(['A', 'B']) // 'A et B'

No locale loads implicitly. Late registration updates availability; existing instances retain their selected data. Both source and precompiled installers preserve string iteration, IteratorClose and UTF-16 parts.

Rust DisplayNames locale data#

Link SDK target :displaynames and install after canonicalization. Load selected JSON text from locale-data/displaynames/ before constructing formatters:

const DisplayNames = Intl.DisplayNames as typeof Intl.DisplayNames & {
  __addLocaleData(...packs: string[]): void
}
DisplayNames.__addLocaleData(frenchJsonText)
new DisplayNames('fr', {type: 'language'}).of('en') // 'anglais'

Locale packs load independently. Existing instances retain their data. Sparse CLDR categories use code/undefined fallback; invalid codes, including lone surrogates, throw RangeError. Source and precompiled installers share the same Rust lookup and validation.

Rust Segmenter#

Link SDK target :segmenter; call formatjs::installSegmenter after canonicalization. For precompiled setup, register js/36-IntlSegmenter.js and call formatjs::installSegmenter(runtime, extensions). ICU4X data and dictionary/LSTM models are static; no per-locale JSON loading is required.

const words = new Intl.Segmenter('ja', {granularity: 'word'})
Array.from(words.segment('こんにちは世界'), part => part.segment)
// ['こんにちは', '世界']

UTF-16 input and indices stay exact, including lone surrogates. Word/sentence boundaries and word-like status may differ from TS; explicit conformance profiles cover both implementations. See the Segmenter port.

Rust Collator#

Link SDK target :collator; call formatjs::installCollator after canonicalization. For precompiled setup, register js/37-IntlCollator.js and invoke formatjs::installCollator(runtime, extensions). CLDR sort/search rules and ICU4X normalization/casing data are compiled in; no locale JSON loading is needed.

const compare = Intl.Collator('en', {numeric: true}).compare
const items = ['item10', 'item2']
items.sort(compare) // ['item2', 'item10']

The bound comparison function is cached, keeps its original instance alive and preserves lone UTF-16 units. See the Collator port for its comparison profile and tests.

Collator requires the Hermes proxy-construction fix in overlay commit 338ff13ff1e996934ae615952d174f8c621844d9 (pending BCR version 260318099.0.0-393a539e6). Use the pinned override from examples/hermes-intl/MODULE.bazel; older overlays perform extra observable newTarget.prototype reads during construction.

Rust NumberFormat#

Link SDK target :numberformat; install after canonicalization with formatjs::installNumberFormat(runtime) or its precompiled-factory overload. js/38-IntlNumberFormat.js registers the individual factory. Ship selected locale-data/numberformat/<locale>.json files and register their UTF-8 text:

const NumberFormat = Intl.NumberFormat as typeof Intl.NumberFormat & {
  __addLocaleData(...packs: string[]): void
}
NumberFormat.__addLocaleData(englishJsonText)
new NumberFormat('en', {style: 'currency', currency: 'USD'}).format(1234.5)

Each pack includes plural rules, so this Rust adapter runs without a JS PluralRules polyfill. Supported locales update as packs load; existing instances retain their selected record when a replacement is registered. Parts and ranges, exact BigInts/numeric strings, localized exponents and rounding run in Rust. The SDK's typed smoke loads English, then French, through the precompiled installer. Linux builds both native artifacts; macOS only runs downloaded smoke.

Native DateTimeFormat SDK#

Retain the DateTimeFormatInstallation guard returned by formatjs::installDateTimeFormat(runtime) on the JavaScript thread. Destroy it before the runtime. For precompiled factories, retain the result of formatjs::installDateTimeFormat(runtime, extensions) after evaluating the SDK extension bytecode. The guard owns thread-bound records; GC finalizers queue cleanup for the JavaScript thread.

Register selected SDK JSON text with these hooks:

type NativeDateTimeFormat = typeof Intl.DateTimeFormat & {
  __addLocaleData(...packs: string[]): void
  __addCalendarData(...packs: string[]): void
  __addCalendarLocaleData(...packs: string[]): void
  __addTZData(pack: string): void
}
const NativeDateTimeFormat = Intl.DateTimeFormat as NativeDateTimeFormat
NativeDateTimeFormat.__addLocaleData(englishJsonText)
NativeDateTimeFormat.__addCalendarData(hebrewArithmeticJsonText)
NativeDateTimeFormat.__addCalendarLocaleData(hebrewEnglishJsonText)
NativeDateTimeFormat.__addTZData(goldenTimezoneJsonText)

Read those texts from locale-data/datetimeformat/en.json, calendar-data/datetimeformat/hebrew.json, locale-data/datetimeformat/calendars/hebrew/en.json and timezone-data/datetimeformat/tz-golden.json. Base locales, calendar providers, calendar locale patches and timezone transitions load independently. Both provider and locale patch are needed before selecting an optional calendar. The SDK ships fourteen optional calendar providers; Chinese, Dangi and Umm al-Qura load their selected tables from the arithmetic JSON packs. No JS NumberFormat or PluralRules installation is needed for native date formatting.

Timezone names initially use UTC offsets until transitions load. Existing formatters see replacement transitions on subsequent calls; range endpoints share one snapshot per call. Defaults start at UTC and can change through Intl.DateTimeFormat.__setDefaultTimeZone. Install a Temporal implementation before the DateTimeFormat adapter when formatting Temporal values. Plain values and Instant retain exact nanoseconds; ZonedDateTime inputs throw TypeError.

The independent SDK consumer exercises source and bytecode installation, locale loading, parts/ranges, DST and Hebrew Adar II names. See its installation example for build and smoke commands.

Native DurationFormat SDK#

Link SDK target :durationformat, include <formatjs/hermes/intl_durationformat.h> and call formatjs::installDurationFormat(runtime) after canonicalization. For precompiled startup, use formatjs::installDurationFormat(runtime, extensions); js/41-IntlDurationFormat.js supplies the standalone factory. No installation guard is required.

Duration metadata is static. Load selected existing number/list SDK JSON text:

const NativeDurationFormat =
  Intl.DurationFormat as typeof Intl.DurationFormat & {
    __addNumberFormatData(...packs: string[]): void
    __addListFormatData(...packs: string[]): void
  }
NativeDurationFormat.__addNumberFormatData(englishNumberJsonText)
NativeDurationFormat.__addListFormatData(englishListJsonText)
new NativeDurationFormat('en', {style: 'digital'}).format({
  seconds: 1,
  milliseconds: 473,
})
// '0:00:01.473'

Read those texts from locale-data/numberformat/en.json and locale-data/listformat/en.json. Duration adds no locale files; its available locales stay static while dependency packs load on demand. Number/list registries negotiate independently. Instances may be constructed before loading; cached formatting profiles retain data after replacement. Arithmetic, padding, sign and parts run in Rust without public JS NumberFormat/ListFormat/PluralRules.

Install Temporal before the adapter for ISO duration strings and branded durations. Otherwise use duration-like records; strings throw RangeError. The independent SDK consumer exercises both installers with selected English/French packs, exact subseconds, negative leading zero, Arabic digits and Finnish time separators.
